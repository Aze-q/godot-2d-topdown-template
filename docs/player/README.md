本文维护《归流》角色系统的运行时架构、公共玩家基础、动作规则、资源契约和联机边界，也是 `docs/player/` 的入口。开发阶段创建新角色的素材标准与流程已独立维护在[新角色创建流程与规范](character_creation.md)。按需阅读见根 [AGENTS.md](../../AGENTS.md)，通用约束见[开发规范](../development/README.md)，玩法事实见[玩法设计](../02_玩法设计.md)，项目目标见[设计思想](../01_设计思想.md)。

创建文档引用本文的运行时契约；同一规则只在所属正文维护，跨任务按引用补读。规范仍全部位于 `docs/player/`，代码与运行资源保留在现有工程目录。

**正式制作方向（2026-09-11 更新）：有限分层图集 + Godot 运行时 Skeleton2D + 同体型共用动作库；少量特殊姿势使用替换帧，武器与元素 VFX 独立。** 本次更新取代“完整身体逐帧为默认、禁止身体分层”的旧约束。PixelLab 负责外观素材及经验证可用的局部修补；Godot 负责绑定、动作播放与游戏表现。

**实现状态：两方向骨骼技术样板已跑通，完整角色系统与全流程自动化尚未完成。** 原有逐帧资源保留作对照，`PlayerAppearance`／`PlayerVisual` 的生产实现仍是 SpriteFrames 版本。有限分层当前由人工编写区域完成，自动分层、遮挡补画、通用绑定导入器和主玩家接入均待完成。角色外观及骨骼动画美术尚未验收，不能登记为正式可用角色。实测记录见[production.json](../../entities/player/appearances/traveler_01/production.json)，历史实验字段保留当时状态；正式方向以本文为准。

## 1. 设计目标与复用边界

新增动作优先增加共用骨骼关键帧；新增同体型角色主要制作方向外观、有限部件、绑定与必要修正，减少为每个角色、每个动作重复生成完整人物图片。节省目标是降低重复绘制与修帧成本，不承诺零人工、任意体型自动重定向或固定比例的总工时节省。

| 可以共用 | 仍需分别制作或验证 |
|---|---|
| 同体型骨骼语义、节点层级、动作时间和 AnimationLibrary | 每个外观的方向纹理、部件区域、遮挡补画、关节位置与必要权重修正 |
| 同一动作的节奏、阶段及通过验证的关键帧 | 各方向的透视、前后遮挡及姿势修正；不同体型的重新适配 |
| 同类武器挂点协议、基本轨迹与动作规则 | 武器方向图、握持长度、双手接触点和特殊外形适配 |
| 公共施法动作 | 火、冰、雷各自 VFX 与音效 |
| 同轮廓的原始图片与限定调色板 | 每个玩家的生命、动作进度、背包、冷却和材质实例 |

首批玩家采用一个基础体型家族。角色创建提供可用外观预设、限定配色和姓名；外观不改变命中范围、速度、资源成本或无敌时间，不新增职业绑定、属性加点或玩家自由拼装身体。制作阶段的身体分层不等于新增换装玩法。NPC 与生物按结构和实际行为选择动作族，不要求全员拥有玩家全套动作；艾妲的足伤不能被健康玩家跑步模板覆盖。

第一版保持剑、大剑、长枪、弓与火、冰、雷。Walk、Run 是表现名称，不新增冲刺机制；梯子与短翻越是场景交互，不能将旧模板独立跳跃键重新引入正式玩法。保留移动与瞄准分离、弓蓄力半速移动、单机及包含房主的最多八人合作。

默认采用有限部件刚性绑定，尽量保持部件自身像素形状。只有刚性关节无法满足已需动作时，才在局部试验少量加权网格或替换姿势帧，并检查像素拉伸。不得把整张人物图的旋转、缩放或拉伸当作八方向身体转向，也不把每个动作重新生成人物全套帧作为默认回退。

## 3. 玩家基础、表现分层与数据流

公共玩家基础继续沿用 `PlayerEntity → CharacterEntity` 与现有玩家场景，不另建平行 `PlayerBase`。新增角色只增加外观资源、兼容骨架与动作映射；输入、移动、攻击、存档和联网逻辑共用。

| 层 | 输入与作用 | 边界 |
|---|---|---|
| 输入与玩家身份 | 本地或远端的移动、瞄准、动作意图 | 不直接扣资源或判伤害 |
| 动作与规则 | 检查状态、成本、阶段与唯一动作时间 | 决定移动限制、取消和发力；不依赖图片或关键帧数量 |
| 实体与结算 | 运动、碰撞、命中、生命、死亡和救援 | 房主／离线本地权威处理有效结果，不让表现重复结算 |
| 角色表现 | 外观图集、骨架、公共动作库、方向修正与规则时间 | 驱动骨骼、替换帧、挂点、武器、VFX 和音效，不反向改变规则 |
| 数据与持久化 | 外观引用、动作定义、成员与世界状态 | 定义可共享，运行状态归实例；不把贴图或节点存进存档 |

```text
输入意图 → 动作规则与唯一时间 → 实体运动／权威结算
                 │
                 └→ 外观＋骨架＋共用动作库 → 骨骼姿势／替换帧／武器／VFX
```

运动方向、瞄准方向、显示朝向分别表达；具体动作决定取哪种方向或保持哪个朝向。人物世界位置以地面原点为准；视觉起伏不能带着碰撞体上下漂移。

正式表现入口继续承担“应用外观、按动作与时间取样”的职责，但需要扩展现有 `PlayerAppearance`／`PlayerVisual` 以接受骨骼资源及独立移动／瞄准信息；具体代码接口在接入时确定，不能将目前三参数逐帧方法当成已支持这些输入。样板的 `sample_visual(action, elapsed, backward)` 仅用于技术试验，`backward` 反向取样不构成正式后退步态。

角色表现内部由四种职责组成，不要求各建一个管理器：骨架保持节点与基准姿势；外观提供图集、部件和绑定；共用动作库提供可取样的关键帧；方向与装备映射提供遮挡、姿势替换和挂点修正。继承玩家基础与复用表现资源是两个层次，不能为每张皮肤复制玩家场景逻辑。

只读纹理、AnimationLibrary、动作规则、绑定定义可共享。每个角色分别持有 Bone2D 姿势、AnimationPlayer／AnimationTree 播放状态、材质参数、动作进度、命中集合与生命。不得在实例动画中修改共用动作资源；需要改变定义时生成新版本。历史 SpriteFrames 与替换帧资源也按只读方式共用。

## 4. 动作时间与事件协议

同一动作规则只有一个时间来源，由游戏逻辑推进；表现根据该时间取样。可以继续使用 AnimationPlayer 和 AnimationTree，但它们不能与状态定时器、AnimatedSprite2D 自由播放同时各自决定同一动作何时发力。接管某动作时，应一并移除该动作旧的计时、无敌和伤害触发入口。

每次动作记录动作标识、规则版本、本次动作序号、所处阶段和阶段进度。阶段至少能表达准备、保持、释放和收招；没有保持阶段的动作直接跳过。需要等待释放的动作可以用保持阶段表达；满蓄力后是否允许继续保持及其上限由各动作规则明确，不能从动画循环擅自推定，也不能循环重播扣费事件。

| 事件 | 规则来源与处理 |
|---|---|
| 接受动作请求 | 检查资源、当前状态和是否允许；生成本次动作序号 |
| 取消 | 按正式规则仅在允许的起手区间生效；未释放的攻击或法术不扣释放成本，闪避自身照常付费 |
| 发力／释放 | 一次扣除对应资源，开始该次攻击的命中窗口或生成箭矢／法术；打空不退款 |
| 受到冲击 | 格挡按实际有效冲击扣体力；不能把格挡待机每次循环当作一次冲击 |
| 命中 | 按本次动作、目标与命中段处理；多碰撞形状不能把同一次命中结算多遍 |
| 命中窗口结束 | 立即关闭本次近战判定，不让整个收招都继续造成伤害；独立箭矢按自己的生命周期处理 |
| 收招结束 | 兜底清理临时动作状态，允许后续动作，不能用它替代命中窗口结束 |
| 饮药生效 | 生效前中断不扣次数；生效时一次扣药并按配方恢复，生效后不返还；不能等到动画结束才治疗 |
| 救援完成 | 核验双方仍有效且未中断，成功时一次扣药并起身；具体成本、生命恢复与中断规则见正式玩法 |

事件跨越时间区间就应处理，不能只检查“当前恰好等于某一帧”。低帧率跳过显示帧时不能漏掉发力；网络重发、重新采样和暂停恢复不能重复触发。每次动作的命中记录随实例保存，不能让 A 的命中结果阻止 B 命中。

正式初值例如闪避总长 0.45 秒、躲避窗口 0.18 秒，必须由公共动作规则定义；躲避窗口放在动作中的具体位置仍待样板确定。人物生成了更多帧，不增加其躲避时长。弓基础蓄力与穿柳弓的不同要求也通过动作规则和保持阶段体现，不复制一套随意变速的结算逻辑。

骨骼关键帧、插值方式、替换帧取样率、各招发力点、取消边界和阶段长度未全部定案。制作时先依据正式已定时间设计节奏，再补未定参数；不能把 PixelLab 默认帧率或 Godot 播放速度当成战斗设计决定。骨骼关键帧数量、屏幕渲染帧率和逐帧图片数量分别记录，三者不等同。

## 5. 运行时资源、骨架与动作协议

### 最小资源契约

| 内容 | 必须明确的信息 |
|---|---|
| 体型与风格 | `body_family`、风格版本、尺寸与可见身高、镜头、比例、像素密度、光源及地面原点 |
| 外观 | 稳定 `appearance_id`、版本、兼容骨架与动作包版本、各方向图集、部件区域与允许配色 |
| 分层与绑定 | 部件语义、原图来源／图集 UV、裁切偏移、旋转支点、骨骼映射、局部基准姿势、必要权重和遮挡顺序 |
| 共用骨架 | `skeleton_version`、稳定骨骼路径、父子关系、角色自身左／右语义、主副手与脚部挂点 |
| 动作库 | 项目动作 ID、动作包版本、规则阶段与时间映射、关键帧、循环方式、上下身轨道范围和方向修正 |
| 例外姿势 | 需要替换的部件或完整短片段、触发阶段、方向、图片帧与挂点映射、回到骨骼的衔接方式 |
| 武器与 VFX | 主／副握点、方向与形态、遮挡关系、事件关联及附着位置 |

这些是数据职责，不要求七种 Resource 或七个 JSON 文件。先使用 Godot 原生场景、纹理和 AnimationLibrary；沿用每角色生产记录追溯来源，稳定重复的结构再提取。资源主键使用英文小写与下划线，如 `traveler_01`、`sword_counter`、`bow_charge_move`；方向为 `s`、`sw`、`w`、`nw`、`n`、`ne`、`e`、`se`。中文姓名和中英显示文本不充当资源主键。

部件选择、遮挡补画、外观提示词与 PixelLab 共用姿势母版的制作方法见[新角色创建规范](character_creation.md)。本节维护这些素材接入运行时所需的接口与约定。

### Godot 绑定与像素质量

采用 Skeleton2D／Bone2D 管理骨架；默认将部件刚性绑定，已有样板使用 Polygon2D 的单骨骼全 1 权重。部件、骨架、父子局部坐标必须一致，Bone2D 写入有效 `rest`，每顶点 UV 与权重数量匹配。Polygon2D 的 `skeleton` 路径相对 Polygon 节点，骨骼权重路径相对 Skeleton2D；路径存在且骨骼已注册后才算绑定成功。[Godot 骨骼教程](https://docs.godotengine.org/en/stable/tutorials/animation/2d_skeletons.html)、[Polygon2D](https://docs.godotengine.org/en/stable/classes/class_polygon2d.html)。

刚性绑定减少部件内部弹性拉伸，但旋转仍会改变像素边缘和贴图原有光照。采用最近邻采样、不启用轮廓抗锯齿，并在原生尺度及实际镜头检查；不得承诺最近邻或像素吸附能消除所有旋转伪影。对不能接受的关节或大幅透视动作，先调层次与支点，再选用局部权重或少量姿势替换；替换范围与原因要记录，不默默扩展成全角色逐帧生产。

### 共用动作库与方向适配

兼容动作库需要一致的骨骼语义、层级、路径、坐标约定与时间协议。两套骨架名称相同不等于自动适配；肢长、基准姿势、披肩轮廓不同仍需调整。主副手及人物自身左右固定，不随屏幕左右互换。

项目动作 ID 与供应商 ID 分离。正式默认动作为 Godot AnimationLibrary 内的关键帧及方向修正，新增 `run`、`cast` 等动作不再自动触发 PixelLab 八向动画生成。各片段明确是否循环；待机、移动、蓄力保持可循环，挥剑、受伤、释放、死亡等按阶段定义结束。不能沿用旧导入器对所有动画写 `loop=true` 的样板行为。

完整人物的八方向外观要求保留。二维骨骼旋转不能生成背面或新的透视：每方向需要相应部件纹理、基准姿势与遮挡配置；关键帧可在经验证兼容的方向间复用，必要时增加方向修正或独立片段。首批先验证一个前斜方向，再验证一个后斜方向，合格后扩到所需八向；同一动画库在 SE／NE 能播放不等于八向美术通过。

方向切换沿用当前动作身份、阶段与时间，同时更新部件纹理、骨骼映射和武器层次；不能因换方向重置蓄力、躲避窗口或重复发力。动作库只驱动视觉骨骼，不直接改写玩家物理实体的世界位置；实际移动继续由规则与实体处理。

上身瞄准／施法与下身移动可按骨骼轨道范围组合。两个动画混合或采样入口不得在无明确规则时同时写同一根骨骼；需要全身协调的闪避、倒地或大幅发力动作优先使用相应全身片段。保持一个调用者时间源，并在动作切换时清除旧姿势残留。

### 八方向与镜像审核

首角色使用八个真实方向与左上光，不镜像。后续外观若考虑只做 S、SE、E、NE、N，再镜像其他方向，必须逐外观、逐动作检查：发型／配件／伤痕能否交换；主副手是否保持；光源是否翻转；武器透视、握点、前后层次和视觉命中方向是否正确。骨骼、挂点、部件映射与纹理必须一起检查，不能仅翻转纹理。

通过才建立镜像映射，未通过则使用独立方向素材。5 组代替 8 组仅说明方向素材组数减少 37.5%，不等于总工时减少 37.5%。开发预览可以只包含指定试验方向并明确缺项；交付则检查所需动作／方向覆盖，不能静默回退左右图。

### 武器与人物对齐

武器独立于身体图集与骨骼动作包，同类武器共享握持协议和兼容轨迹。武器仍可能需要多个方向及状态，例如弓未拉开、蓄力与释放；不能按“二十把武器只需二十张 PNG”估算。同类握柄、长度和双手距离尽量统一，超出范围重新适配。

武器挂在语义明确的主手挂点上，副手按动作与武器副握点约束；需要时使用经验证的 IK 或修正姿势，不能只把武器跟随一只手就算双手握持完成。遮挡依据方向和动作阶段调整，必要时使用局部遮挡蒙版或手部替换图；不能让武器永远浮在人物前方。人物自身手性、持弓手和拉弦手保持一致。

武器轨迹与命中形状遵循同一动作定义，但不能从刀刃像素或骨骼位置自动生成权威伤害。更换剑外观不改判定范围；破桩大剑直砸、回扫枪横扫等行为变体仍需对应发力与命中形状，不能只换特效。

## 6. 动作覆盖与上下身组合

下表列的是玩法所需表现，不是要求每项制作独立文件，也不要求所有场景交互一律生成八向。

| 动作组 | 必需覆盖 | 可以复用的部分 |
|---|---|---|
| 基础移动 | 待机、普通移动、闪避；Walk／Run 按实际用途使用 | 同体型节奏、方向规范和合格的镜像 |
| 剑 | 普攻、格挡保持、受挡反馈、反击；灰烬剑第三段连击反馈 | 相同握持与准备姿势，元素通过特效表达 |
| 大剑 | 普攻、蓄力、保持、横扫重击、直砸重击 | 部分准备姿势；两种释放动作分别表达 |
| 长枪 | 普攻、架枪、迎击／突刺、横扫变体 | 相同持枪姿势，释放动作按形状区分 |
| 弓 | 快射、拉弓、保持、释放、蓄力移动 | 保持阶段承载不同蓄力时间；箭矢独立 |
| 魔法 | 施法准备、释放与收招 | 火、冰、雷使用公共人物施法动作 |
| 生存与合作 | 受伤、饮药、倒地、救援、起身、死亡表现 | 静止保持或短循环；倒地和死亡逻辑独立 |
| 场景交互 | 操作机关、梯子、短翻越 | 仅按场景真实需要覆盖方向 |

`Charge` 表示可以复用的逻辑阶段，不意味着举大剑、拉弓与施法必须用同一张身体姿态。

**弓蓄力移动是首批必测项。** 骨骼允许上身拉弓、下身运动分开制作，但需要验证瞄准与前进、后退、侧移的真实组合。倒放跑步循环不等于合格后退步态；腿会动也不等于脚底锁定、双手接触和出箭点正确。

保留移动与瞄准分离、弓蓄力半速移动。先用前进、后退和侧移的代表组合验证腿部姿势、上身保持与遮挡，再扩充覆盖表；不直接采购 8 朝向 × 8 移动方向全套图片，也不通过禁止移动或自动改变瞄准方向消除制作难点。

无输入保持稳定朝向，方向边界不能因微小输入来回切换。死区、方向切换条件和动作中转向限制通过样板确认，不由图集导入器决定。

## 7. 在现有项目中逐步落地

1. **完成可复用的美术与骨架基准。** 沿用现有两方向技术样板，补遮挡区域、关节、接地、透视和武器挂点；先验前斜、后斜，处理当前缺陷，再扩到八方向。按[创建流程的阶段记录](character_creation.md#4-pixellab-mcp-自动化制作规范)登记完成情况。
2. **验证第二个外观。** 同体型但发型／衣服轮廓明显不同，接入同一骨架规范和动作库；测量新增部件、绑定调整与修图工时。只有一个角色的两个方向不能证明跨角色自动适配。
3. **提取已稳定的共享内容。** 将样板中的动作定义移入现有公共动画目录，把角色专属部件与支点从硬编码迁入外观数据；按实际重复需求补导入工具，不先建大型通用框架。同步版本与依赖，重导入不覆盖已接受资源。
4. **接入 PlayerEntity。** 扩展既有表现入口，分开移动／瞄准／显示方向；统一基础剑、闪避的动作时间、取消、发力和结算。替换对应旧动画、攻击无敌与伤害入口，不让两个表现系统同时控制同一动作，不恢复旧独立跳跃玩法。
5. **验证动作组合与多端基础。** A／B 与一个有效动作接通后立即验证房主／客机、成员身份、权限、重连与重复事件；同时完善双手武器及弓蓄力前后侧移，不等全套素材完成再开始联网。
6. **补齐覆盖与验收。** 接入其余武器变体、三元素、生存合作和场景交互；逐项检查时间、资源成本与结算边界，随后验证配置上限与房主加七名客机。
7. **创建、持久化与启用。** 在真实存在合格 A／B 后接入预设、限定配色与姓名，保存外观／骨架／动作包引用及版本；按验收记录登记可用外观，保持成员装备和解锁的世界边界。

这些是依赖顺序，不要求一次实现全部。保留可运行的旧入口与对照资源，按动作和资源版本逐步替换；迁移前检查 NPC 与敌人对共享基础类的引用，避免只修玩家而破坏其他实体。

## 8. 联机、身份与存档约束

离线与联机使用同一套动作定义。联机时客户端提交意图，房主确认命中、扣费、状态和救援；远端可以播放或做有限表现预测，但不能因此重复产生伤害。动作序号与事件标识用于识别重复消息；本地与远端不能各播一次相同命中特效而叠加成两次。

同步动作标识、版本、开始／阶段时间、移动与瞄准方向、外观引用、装备和必要状态；各端按共同动作资源驱动自己的骨骼，不发送动画图片。各端使用相同资源映射；资源版本不兼容时应明确提示，不能让双方使用不同规则继续结算。具体传输、插值和预测方案在网络样板中选择，不在本文空建一套网络框架。

房间配置上限为 1～8，含房主。旧 `player_id` 只是模板实例编号，网络连接身份、世界成员身份和可携带外观应明确区分。房主退出后客人不能继续运行该房主世界；重连遵守正式玩法中的资源和倒地状态，不靠重新实例化人物补满资源。

姓名和外观可沿用，但保存一个外观引用不等于发放对应购买权益。正式经济包含三件可购买个人外观，它们与创建预设、跨世界沿用的具体解锁归属尚需细化；在实现购买或解锁前确定该规则，不能擅自做成全局解锁，也不能擅自要求每个世界重复购买。

八个角色实例同屏用于检查清晰度、独立材质与性能；只有多个实际连接端的输入、权限、事件和同步检查才能证明联机工作。更不能把八种外观等同于支持八人。

## 9. 验证与制作记录入口

资源或表现实现变更需检查真实骨骼绑定、相同时间取样、方向切换、实例隔离及实际画面；动作结算变更还需覆盖第 4 节事件边界，联机变更遵守第 8 节。按改动范围验证，不把编译通过或同屏实例当作美术与多端验收。
