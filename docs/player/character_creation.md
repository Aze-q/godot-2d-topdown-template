# 新角色创建流程与规范

本文用于开发阶段根据提示词制作、绑定并登记新的角色外观，也用于修复已有素材、制作共用动作母版和执行 PixelLab MCP 自动化。玩家基础类、运行时资源契约、权威动作时间及联机规则由[角色系统开发规范](README.md)维护；开始任务先读[通用开发规范](../development/README.md)。

| 需要做的工作 | 对应章节 |
|---|---|
| 准备角色提示词与制作参数 | [创建基准](#1-创建基准与首角色) |
| 准备可绑定的角色部件 | [有限分层与遮挡补画](#2-有限分层与遮挡补画) |
| 制作可复用的动作来源 | [PixelLab 共用动作母版](#3-pixellab-animate-with-skeleton-与共用动作母版) |
| 执行生成、导入、恢复与预算检查 | [MCP 自动化制作流程](#4-pixellab-mcp-自动化制作规范) |
| 检查完成情况与制作成本 | [验收](#5-验收与待完成事项)、[样板证据](#6-已有样板成本数据与排查依据) |

**当前状态：已有首个候选角色及两方向骨骼技术样板，素材美术与完整自动化尚未验收。** 后文区分可直接使用的工具、需要继续制作的步骤和仅作说明的例子；详细数据以角色生产记录为准。创建角色仍遵循已确认的有限分层与运行时骨骼方向。

## 1. 创建基准与首角色

每次提示词由固定项目风格与本次外观描述合并，制作参数单独提交。固定风格只在视觉基准正式调整时改版，不让每次外观生成自行改变比例或镜头。

| 固定项 | 当前规范 |
|---|---|
| 美术与镜头 | 奇幻探索 ARPG 的纯 2D 像素美术；有手工绘制感、体积与前后层次，不能像 3D 模型像素化。相机固定 `low top-down`，以工具视角及首个基准图为准，不再叠加可能冲突的“精确 35°”要求 |
| 比例与结构 | 成年人的自然比例，偏修长但能清晰辨认；可见部分头顶、脸部、肩胸、手臂、腿脚，站地稳定、剪影清楚；禁止 Q 版、Chibi、夸张大头与过度可爱农场比例 |
| 像素与明暗 | 中等细节、像素块清楚、选择性深色描边；左上光源，中等饱和度且略去饱和的奇幻配色。禁止抗锯齿、模糊、平滑边缘、粗纯黑轮廓、微小噪点堆砌和只有一层平涂的阴影 |
| 外观参考图的构图与身体 | 单人、完整全身、居中、透明背景；手中无物，身体不画入剑、弓、杖或盾。禁止场景、UI、文字、名字、边框、海报与多人物 |
| 排除风格 | 禁止 3D 渲染、写实照片、平滑数字绘画、矢量插画、标准动漫立绘、严格等距、横版侧视、纯正面立绘、复杂重甲和霓虹高饱和色 |
| 生成规格 | PixelLab `Sprite Size = 128px`／`size=128`，八个真实朝向。实际输出宽高、可见人物高度、脚底坐标、扩边及模型模式写入生产记录；不把尺寸选项等同于最终裁切规格 |

首角色内部资源标识为 `traveler_01`，不将此标识画到图片上。外观描述固定为：约 23 岁的年轻男性旅行者，偏瘦但有运动感；中短、略凌乱的深棕近黑头发，清秀成熟的五官与干净脸型，神情冷静、安静而警觉。暖灰短旅行披肩配蓝灰围巾、浅灰内衬、深灰棕旅行服、棕色皮腰带与小工具包，深色长裤、磨损棕色旅行靴、轻量护腕；整体沉稳低调、可靠且有探索经验。首样板不加单肩甲，披肩保持短小，避免遮住握点；不携带武器，不限定武器类型，也不由此外扩职业系统。

本角色采用左上光与可辨认的工具包，首角色外观参考的八方向均独立生成和检查，不镜像；骨骼实现目前只覆盖 SE／NE。后续外观仍按[系统的镜像审核规则](README.md#八方向与镜像审核)逐动作核对镜像资格；不为节省首样板资源把已确认左上光擅自改成顶部光。

上述“完整全身、单人”用于外观参考图。制作部件图集时另加分层输出要求：按所属方向、角色比例和颜色补齐可动部位与遮挡区域，避免部件粘连、截断关节或误带其他部件；不能直接把完整人物提示词当作可靠的自动拆分指令。图集内可以包含同一角色的多个部件，但重组后的角色须与已审核参考一致。

## 2. 有限分层与遮挡补画

首批以头、胸腹／髋部、两侧上臂／前臂、两侧大腿／小腿作为最小分层参考，手和鞋可先与对应末端部件合并；握持或足部姿态确有需要时才补少量替换图。围巾、工具包、短披肩优先跟随所属身体部位，只有已需动作会产生独立摆动或遮挡问题时才拆分。样板的 11 区域是实测起点，不是每个角色必须遵守的部件数。

部件可打包进同一角色图集，必要时按方向分图集；部件数不等于 PNG 文件数。骨骼和部件按功能分层，不能演变成逐根头发、每件饰物都独立维护的素材树，也不因此开放玩家自由拼装身体。

从完整图裁出可见区域只是第一步。手臂移开后的衣服、弯曲关节内部、腿部遮挡和其他原图不存在的像素必须补画，接缝保留合理重叠。部件轮廓不得误带躯干、腰包或另一肢体；拆完后重组基准姿势，先核对与参考图一致，再测试最大弯曲与遮挡。仅将原图硬切成区域不能标成“分层完成”。

坐标统一为 Godot 2D 的 X 向右、Y 向下。纹理裁切或图集打包时保留原始偏移，地面原点、关节、挂点与 UV 坐标转换必须可还原；不能自动居中每个部件造成角色装配或脚底漂移。`size=128` 不等于必须把真实输出裁为 128×128。

部件准备完成后，绑定须符合[运行时资源契约](README.md#5-运行时资源骨架与动作协议)与[Godot 绑定要求](README.md#godot-绑定与像素质量)；需要的动作、方向和武器挂点分别按系统文档对应章节检查。

## 3. PixelLab Animate with Skeleton 与共用动作母版

需要设计或修正动作时，允许使用 PixelLab **Animate with Skeleton** 制作可复用的姿势母版，再用于其他兼容角色。母版描述“身体如何运动”，人物外观描述“角色长什么样”；二者独立保存与版本管理。Godot 运行时骨骼继续作为默认播放方式，不因为使用 PixelLab 制作母版而恢复逐角色生成全套动画的流程。

官方说明支持将骨架姿势保存为图片或 Aseprite 文件，并在精确名称为 `Pose - PixelLab` 的图层中用于其他角色。这属于带图层和时间轴的编辑器制作流程，与 Character Creator 或 MCP 的输入能力要分别核实。[Animate with Skeleton 官方说明](https://www.pixellab.ai/docs/tools/animate-with-skeleton)。

| 资源 | 可复用内容 | 与 Godot 的关系 |
|---|---|---|
| PixelLab 官方动作模板 | 服务已有模板的姿势与运动参考，以真实 `template_animation_id` 选择 | 可经 MCP 生成参考或必要补帧；输出图片不含已验证可导入的 Godot 绑定 |
| PixelLab 编辑器姿势母版 | 已保存的骨架姿势序列，保留方向、比例、节奏和可编辑来源 | 可作为公共动作制作参考；需在 Godot 单独制作关键帧，或通过之后验证的转换程序映射 |
| Godot 共用骨架与动作库 | 稳定骨骼层级、基准约定、AnimationLibrary 与方向修正 | 运行时直接复用；新外观仅补部件、绑定与适配，通常无需再调用 PixelLab 生成该动作 |
| 按角色生成的特殊姿势帧 | 指定外观、方向与阶段的像素结果 | 用作例外替换帧；不同外观仍需自己的图片，不能误算为共用骨骼关键帧 |

当前没有验证过 PixelLab 姿势文件直接导出 Godot 骨骼层级、rest、网格权重或 AnimationLibrary；也没有已实现的自动转换器。制作参考可以来自 PixelLab，运行时资源仍需实际建立、映射和验收。只有 PNG／GIF 时不能把图片里可见的骨架当成已有数值骨骼轨道；不虚构自动提取结果。Godot `.tres` 同样不能直接充当 PixelLab 的自定义骨架输入。

母版与公共动作资源归现有 `entities/animations/` 的对应体型／动作包；PixelLab 源文件放该动作包的制作源区并排除运行时导入，供所有角色引用。角色 `production.json` 只记录所用母版版本及本角色修正，避免为 A、B 各复制一份可独立改动的公共母版。此处是目录职责，不预建空文件；取得真实源文件后再保存。

| 母版最小记录 | 要求 |
|---|---|
| 项目身份 | 项目母版 ID、revision、动作 ID、体型家族、兼容 Godot 骨架版本；项目 ID 不冒充供应商模板 ID |
| 来源 | 直接在 Godot 制作、PixelLab 官方模板或 PixelLab 编辑器姿势；官方 ID／真实源文件路径、版本与散列，必要的来源信息 |
| 坐标与方向 | 相机视角、方向、工作画布、地面原点、人物自身左右、与外观原图的偏移及比例映射 |
| 动作约定 | 源姿势序列、规则阶段／时长映射、是否循环、手脚接触点和上下身适用范围；源帧数不等于规则时长 |
| Godot 结果 | 已建立的动作库及片段、骨骼映射、方向修正；未完成留为待制作，不填写不存在的资源路径 |
| 验收与依赖 | 候选／可用版本、验证过的外观版本、动作／方向缺项与失败原因；母版变更需检查其依赖 |

上述是项目记录要求，不是新增 PixelLab MCP 参数。首个角色验证通过时记为“单角色候选母版”；至少两个同体型、轮廓不同的外观通过相同动作约定后，才能标为跨角色可复用。不得因换人物而修改公共动作时间；肢长、衣物和支点修正归角色适配，公共运动方式改变则发布新母版／动作库版本。

编辑器姿势工程的画布需与角色创建选项分开记录。官方教程列出的画布为 16、32、64、128、256 的正方形；当前角色原图实际 180×180，不能因 Sprite Size 选了 128 就缩成 128。若采用 256×256 工作画布，可先验证四周各留 38 像素、保持原像素大小的映射：原地面点 `(90,174)` 对应 `(128,212)`。这是工作画布适配例子，尚未执行；不修改项目镜头、身体比例或默认生成模式。[工具尺寸限制](https://www.pixellab.ai/docs/tools/animate-with-skeleton)。

**Run 母版复用示例。** 下列流程说明制作职责，`adult_traveler_run_v1` 是示例项目母版名，尚未创建或验收，不是 PixelLab 官方模板 ID。

1. 先查体型 `adult_traveler_v1` 是否已有合格的 Godot `run` 动作；已有则直接适配新外观，不重新生成 Run。
2. 缺少满意的跑步姿势时，可使用 Animate with Skeleton 编辑器的参考骨架、官方预设或手工修改来制作母版。先核对角色关节、视角和一个前斜方向的姿势与循环，再检查后斜方向；保存可编辑姿势源，不为每个角色从头重新设计跑步。
3. 把通过检查的母版动作落实为一次公共 Godot `run`：映射骨骼、基准坐标、手脚接触与规则时间，补必要方向修正。当前此步骤需要实际制作，不能将 PixelLab 生成的 8 张人物图改名后称作骨骼动作库。
4. 角色 A 的分层外观 + 公共骨架／Run，形成 A 的跑步；角色 B 的分层外观 + 同一公共骨架／Run，形成 B 的跑步。分别检查接缝、脚底、衣物、方向和握点；两角色共用的是动作库，外观和绑定修正仍各自维护。
5. 只有动作确实需要骨骼难以表达的特殊姿势时，才用同一母版为相应角色制作所需替换帧，单独记录生成范围与费用。复用母版不意味着这些图片免生成或免计费。

首批旧 MCP 请求为 `idle → breathing-idle`（每向 4 帧）、`run → running-8-frames`（每向 8 帧），这不是今后所有动作的固定帧数；旧 Run 候选有明确视觉缺陷，不能直接登记为合格母版。编辑器具体操作和 MCP 自动执行边界见[自动化流程](#4-pixellab-mcp-自动化制作规范)。

## 4. PixelLab MCP 自动化制作规范

### 默认流程与能力边界

目标流程为：**需求与版本 → PixelLab 外观参考 → 有限分层／遮挡补画 → 共用骨架绑定 → 动作库适配 → 少量方向验收 → 完整覆盖 → 玩家接入与登记。** 八面参考图用于统一外观；不再要求把每一面送入 Animate with Skeleton 生成所有动作。共用动作在 Godot 落地和取样，需要时采用[共用动作母版](#3-pixellab-animate-with-skeleton-与共用动作母版)作为制作来源。

PixelLab 操作使用其官方 MCP，Godot 连接与实际运行使用 Godot MCP，文件整理与导入可由本地脚本完成。通过本地客户端发送官方 MCP JSON-RPC 仍属于 MCP；不擅自换成其他生成服务。能力以[官方 MCP 文档](https://api.pixellab.ai/mcp/docs)和本次真实 `tools/list` 为准，网页功能、历史字段或服务宣传不能替代当前账户接口确认。

本规范定义要实现的流程。当前已有 MCP 创建／查询／下载、旧逐帧导入和骨骼技术样板；**自动拆分、遮挡补画、通用绑定、阶段调度及预算拦截尚未实现**。发现接口缺少关键输入时，先补接入或做已授权范围内的局部试验，保留具体阻塞；不能通过生成整套动画绕过，也不能把脚本占位写成全自动完成。

| 阶段 | 输入 → 工作 → 输出 | 进入下一阶段的条件 |
|---|---|---|
| 1. 创建计划 | 提示词、外观 ID、风格／体型／骨架／动作包版本、所需覆盖 → 合并已有决定 → 本次生产计划 | 区分新增外观、新增动作或修复；已有素材与有效回执优先复用；标明试验范围和已授权生成预算 |
| 2. 能力核实 | 当前 MCP schema、余额、在途任务 → 检查创建／编辑／下载所需输入及本地接入 → 可执行步骤 | 不补造不存在的参数；预算未知或关键能力未接通时，不提交无法继续的扩展批次 |
| 3. 外观参考 | 已定风格与本次外观 → `create_character` 提交 `size=128`、`low top-down` 与八方向 → 角色 ID、回执、原图与元数据 | 已有 `traveler_01` 先查询／下载复用；真实画布、方向、全身、身份、配件、光源、空手和像素风格检查通过 |
| 4. 分层与补画试验 | 已审核参考 + 部件约定 → 先做一个前斜方向的可动区域和遮挡补画，再做后斜 → 部件候选与来源映射 | 基准重组正确、没有误带身体碎片、关节极限不露空；不能仅凭有透明通道判为通过 |
| 5. 骨架与绑定 | 部件／图集、共同骨架版本 → 配置基准姿势、UV、权重、手脚挂点与层次 → 候选 Godot 资源 | 路径、权重与坐标有效，源像素／偏移可追溯，动作驱动真实骨骼；新角色不能盲套上一角色的裁切坐标 |
| 6. 动作适配 | 查已有合格动作库；缺动作时执行下方母版分支 → 制作／复用共同动作并适配方向和武器 → 方向适配结果 | 原生与地图尺度检查接地、接缝、透视、手性和上下身组合；库里有动作名称不等于动作质量通过 |
| 7. 扩充覆盖 | 已通过的少量方向 + 本阶段所需覆盖表 → 补齐其余方向和必要姿势 → 完整候选 | 移动满足八方向；梯子等按实际所需方向；每项缺失显式记录，失败方向留在候选状态 |
| 8. 集成与登记 | 合格外观／绑定／动作版本 → 接入共用玩家、验证实例隔离与所需游戏行为 → 可用版本 | 满足本阶段技术与视觉验收，更新可用引用；完整角色交付还须通过[验收清单](#5-验收与待完成事项)全部相关项目 |

首外观基准及新的公共动作基准按用户已有审核约定执行；现有基准内的查询、下载、整理、已授权修复不逐次请求许可。新的制作范围、超出预算或改变已确认风格时才说明具体差别并确认。自动流程的通过条件是质量检查，不是每一步都要求用户点击。

PixelLab 局部编辑／补画仅在真实 MCP 暴露并且本地客户端支持相应工具后使用；即使工具能编辑图片，也不能据此声称能直接导出语义分层图集或 Godot 权重。当前样板仅演示原图区域绑定，不证明这一步自动化成立。已有局部修复无法满足美术时保留失败原因和已做结果，不无限重试。

### 动作母版的自动化分支

1. **先复用已通过的运行时动作。** 根据动作 ID、体型、骨架和动作包版本查询公共资源；兼容时直接做本角色适配，无需调用 Animate with Skeleton。已有源母版但没有 Godot 结果时，任务状态仍是“待运行时制作”。
2. **确需官方模板生成参考或补帧时走 MCP。** 当前 `animate_character` 支持 `mode="template"` 与真实 `template_animation_id`，必须显式传入本批 `directions`，先单方向试验，避免省略方向触发整组生成。源参考、任务、输出和费用绑定同一母版候选版本；它调用后产生图片，不产生已完成的 Godot 动作库。
3. **准确解释模板参数。** `ai_freedom=0` 可作为按模板试验的起点，但不能保证外观、配件和方向完全正确；模板模式使用模板自己的帧数，`frame_count` 不会将它改为指定帧数。动作的时间、循环和验收仍按项目协议执行。[当前 MCP 参数](https://api.pixellab.ai/mcp/docs)。
4. **自定义编辑器母版单独核实输入通道。** 本次公开文档和已有工具发现记录没有自定义骨架图片、Aseprite 工程或关节序列上传字段，也没有已接通的 Godot 转换器。不能把 `adult_traveler_run_v1` 等项目 ID 填入 `template_animation_id`，或用文字动作、首尾图片输入冒充整套骨架复用。将所需能力标为待接入；可继续制作 Godot 动作及其他不依赖该输入的工作。
5. **保持执行方式可追溯。** 如后续采用编辑器制作母版，记录实际编辑器、源文件和 `Pose - PixelLab` 图层，不标成 MCP 自动完成；在当前要求全程 MCP 的范围内，不能静默切换为 UI 操作。只有真实接口支持所需输入并完成小样验证，才能增加该自动化步骤。
6. **只扩通过的母版。** 先完成少量方向和 A／B 外观复用验收，再扩充覆盖或特殊姿势帧。母版一次制作、角色分别适配；失败定位到母版、角色绑定或特定生成帧，不重做所有角色的全部动画。

分支状态至少区分“姿势源已取得”“Godot 动作已建立”“单角色验证”“跨角色验证”，不以保存一个骨架文件替代全部完成状态。当前骨骼样板的动作直接在 Godot 编写，没有 PixelLab 编辑器母版导入记录。

### 状态、版本与断点恢复

每外观沿用一份 `production.json`；下列字段是新流程的最小数据要求，**尚未全部在脚本中实现**。既有记录以扩展字段兼容迁移，不能覆盖原始回执或把旧失败状态改成通过。

| 数据 | 要求 |
|---|---|
| 身份与依赖 | `appearance_id`、候选 revision、风格／体型／骨架／动作包版本、母版 ID／版本，接受版本引用；记录依赖哪些共同资源 |
| 本次范围 | 制作类型、试验／交付阶段、所需动作与方向、例外补帧清单和生成预算；不设全角色统一 8 帧 |
| 阶段状态 | 每阶段待处理／进行中／待视觉检查／通过／失败／阻塞，及阻塞原因；通过前不推进依赖阶段 |
| 来源与请求 | 原始需求、合并提示词、输入图片与散列、母版来源及实际接入方式、工具 schema／模式、请求指纹、远端 ID、回执、尝试关联和时间 |
| 部件与绑定 | 图集／区域／偏移／挂点、遮挡补画来源、绑定资源路径、骨架版本和角色专属修正 |
| 验收与成本 | 自动检查和视觉结论分别记录，失败动作／方向／部件定位，实际账户差、可获取的逐任务费用及人工工时 |

对同一输入与版本，先查已有阶段输出和远端任务，再决定是否需要提交。超时可能已受理，应标记提交状态未知并查询原任务；无法确定时只阻塞依赖的提交，继续不依赖它的本地工作。确认未受理、失败或缺失后才建立新的 attempt；不能改回执文件名绕过未知状态，也不能因下载失败重新付费生成。

生产必须写入候选版本；接受版本继续可用，验收通过后才切换引用。改变公共骨架、动作库或图集布局时明确受影响外观与动作，重新检查这些依赖；仅改配色不重生成动画，仅改武器外观不重生成身体，仅改动作关键帧不重画所有外观。确需新增姿势图时只处理对应例外，不重跑全部角色。

### 预算、队列与失败处理

预算按已授权范围和实际可查询的计费单位记录；未知单位不换算为美元。制作前估计所需远端作业，分阶段提交，阶段结束核对余额变化后再扩充。图片帧数、MCP 调用数、生成槽位与扣费单位分别统计，不能把“640 帧”写成“640 次付费调用”，也不能将减少帧数视为同比节省费用。

首批账户并发实测为 8，一次八向动画占 8 个槽位；后续以实际队列为准，不能把 8 固定成永久服务上限。回执 `status=returned` 只表示 MCP 返回，仍需检查 `result.isError`、任务 ID 和最终状态。已明确容量拒绝而未创建任务时，等待槽位后可在原范围内新建 attempt；已受理任务继续查询。

生成拒绝、下载受限、文件损坏、视觉失败分别处理：权限或下载错误先解决取回已有资产；文件结构错误重取并核验；视觉错误只修复受影响方向或部件。曾出现单图 CDN 403，官方 ZIP 可取回；角色仍有动画在途时 ZIP 返回 423，须等待原任务结束，不重建角色。

本地客户端已具备同一路径回执独占写入、相同已返回请求复用和未知提交保护；不同回执路径之间尚无全局去重。跨阶段调度、预算拦截、验收门禁和只重建受影响资源仍是待实现项，不能依靠一份 JSON 配置就声称程序已经强制执行。

以下是已存在的首角色查询与下载命令，从仓库根执行；仅取回已有资产，不是新骨骼流程的一键入口。未运行的命令不能写成完成记录。更换机器时选择满足 Python 3.11+ 的本地运行时；旧逐帧导入另外需要 Pillow。

## 5. 验收与待完成事项

| 项目 | 通过条件 |
|---|---|
| 外观与分层 | 重组后符合参考；遮挡补画完整；不误带身体碎片，透明边缘、原点与图集偏移正确 |
| 骨架与动作 | 骨骼／权重／UV 有效；关节大幅运动不露空；无残留姿势、错误手性和不可接受的像素拉伸 |
| 方向与接地 | 所需八向覆盖、前后层次与切换透视正确；真实地图尺度接地稳定，转向不突变，脚底滑动在目标质量内 |
| 跨外观复用 | A／B 引用同一母版版本及兼容动作库，动作规则不变；记录每个外观的绑定与姿势修正，不能将两方向等同两角色；使用 PixelLab 时，姿势源与 Godot 结果的映射可追溯 |
| 武器与元素 | 同类两种武器不重新生成身体；主副手、八向遮挡与释放点正确；火冰雷共用人物动作 |
| 弓蓄力移动 | 前进、后退、侧移均保持独立瞄准、双手接触与正确步态，半速限制来自规则 |
| 时间与结算 | 取消、保持、掉帧、暂停恢复不漏扣或重复扣费；近战窗口、药瓶、救援只结算一次 |
| 实例与联机 | A 的姿势／材质／命中不影响 B；房主与客机检查权限、重连和重发，容量验收为房主加七名实际客机 |
| 自动化恢复 | 复用已有任务和通过资产，未知受理不重复提交；质量失败不推进；预算与受影响资源重建按记录执行 |
| 性能与成本 | 同镜头、同角色数量测实际帧时间、内存／纹理及绘制开销；分记生成、补画、绑定、方向和动作修正工时，不以文件数推算帧率 |

验收区分自动技术检查、视觉审核、实际地图测试和玩家反馈；文件可读或程序启动不代表好看、好玩。八个同屏实例只证明该场景表现，不证明八人联网。相同外观可以共享只读纹理，但骨骼与绘制仍有实例开销，须实测。

当前必须补齐：首角色外观签收；统一地面原点和地图尺度；有限分层与遮挡补画方法；稳定骨架语义／关节／支点；八方向透视与遮挡；脚底接触；双手武器和持弓步态；第二外观适配；新流程导入、门禁和预算恢复；主玩家及网络接入。限定配色、个人可购买外观的解锁归属与剩余动作时间参数沿用系统文档的[动作时间](README.md#4-动作时间与事件协议)和[联机、身份与存档](README.md#8-联机身份与存档约束)边界。

这些是已选方向下待实现或验证的事项，不是允许删减已批准玩法的空白。若实际质量或制作成本要求再次改变正式方案，应提供样板证据、影响范围和具体替代方案供用户决定。

数学估算：若逐帧制作 10 个动作 × 8 方向 × 8 帧，为 640 张最终画面；按本角色 180×180 RGBA8 满画布计算约 79.1 MiB，不含压缩、mipmap 和其他副本。这不是实测显存，也不是 640 次接口调用。骨骼减少新增动作所需身体图片，但总工时仍包括分层、补画、绑定和方向修正，待第二外观及更多动作测量后判断收益。

排查确认：旧流程没有把每个动作强制为 8 帧；跑步的帧数由所选预设决定。真正限制是旧导入器要求所选动作八方向齐全、只输出 SpriteFrames，以及缺少小批次质量／预算调度。这些工具能力在[自动化流程](#4-pixellab-mcp-自动化制作规范)中保留为历史与迁移说明，不再代表正式默认制作路径。
