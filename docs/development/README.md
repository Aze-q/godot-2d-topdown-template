# 通用开发规范

适用范围：本仓库。当前项目为《归流》（工作名），基于 Godot 俯视角 2D 模板开发。每次任务先阅读本文，再通过根目录 [AGENTS.md](../../AGENTS.md) 按需选择相关文档。

## 文档职责与读取范围

读取条件统一维护在根索引，不在本文重复登记模块清单。不预读全部子系统；跨系统任务只补读受影响模块。具体规则回到所属正文查阅，不能只依赖索引摘要。用户当前会话中的明确决定优先于旧文档。出现冲突时说明冲突点，按已有授权更新所属正文，不能悄悄混合两个版本。模板自带功能和上游 README 不是本作玩法决策。

## Think Before Coding：先理解再实现

1. 开始前说明本次目标、关键假设、涉及文件和验证方式；先查看相关代码与工作区改动。
2. 不隐藏不确定性。若歧义会改变用户体验、数据含义或制作范围，列出具体差别并提出问题；不把猜测写成已确定事实。
3. 有更简单的实现时说明取舍，优先沿用现有场景、资源与脚本。已获授权的常规、可逆实现细节自行完成，无需反复确认。
4. 区分“设计已确认”“实现已完成”“检查已通过”“玩家已验证”。文档确认不等于功能完成，程序能运行不等于好玩。
5. 新玩法与剧情提案先讨论，用户确认后再成为正式基线。实现已确认设计时不因普通技术选择重复请求设计批准。

## Simplicity First：最小必要实现

1. 只实现本次任务需要的内容。不预建通用框架、任意扩展槽、额外职业或尚未采用的系统。
2. 逻辑分层不要求每层都建立一个类或节点；共享实际重复的逻辑，避免一次性抽象。
3. 不为假设中的异常增加复杂分支；真实存在的断线、重复事件、存档失败按所属规则处理。
4. 配置项只为明确需求或实际调参服务。房间上限 1～8 是明确需求，其他配置不据此无限扩张。
5. 新文件按职责放置，有实际内容后再建立子目录。规范放在 `docs/`；代码与运行资源沿用现有职责目录，不为文档整理再建一套平行运行系统。

## 实现必须遵守的边界

- 项目范围以[设计思想](../01_设计思想.md)为准：单人开发，Steam，中文与英文，完整离线单机与包含房主的最多八人好友 PvE。功能完成情况以实际验证为准。
- 武器、元素、移动和交互规则以[玩法设计](../02_玩法设计.md)对应章节为准；不能因模板已有 Run、Jump 或工具示例中出现其他元素，就自动扩大本作范围。
- 角色采用有限分层与 Godot 运行时骨骼的制作方向；共享动作、外观公平性、镜像、握点、双手武器、前后遮挡及弓蓄力移动执行[角色系统开发规范](../player/README.md)，素材制作与自动化执行[创建新角色流程与规范](../player/character_creation.md)，不在本文维护第二份角色规则。方向确认不等于全自动流程已实现，两方向技术样板不等于完整角色验收。
- 状态变化只有一个权威结算入口；表现层不独立扣资源、造成伤害或发放奖励。联机权限和事件重入遵守所属玩法规则，角色动作的唯一时间协议见角色系统开发规范。
- 只读定义可共享；生命、动作进度、领取状态等可变数据归实例或该世界成员，不能写入共享定义资源。具体数据归属按相关子系统规范落实。
- 联机身份与存档边界以玩法正文为准；不能把临时连接编号当作永久成员身份，也不能因为外观可沿用而擅自让装备与进度跨世界携带。

## 代码与资源工作方式

- 使用 GDScript，遵循邻近代码的命名和缩进。新增方法、资源与信号表达明确职责；注释解释必要原因。
- 保留与当前任务无关的用户改动。修改共享实体前检查玩家、NPC 与敌人的使用点，避免只修玩家却破坏其他实体。
- 不直接修改 `.godot/` 生成缓存。移动或替换资源时同步检查场景引用、资源路径与 UID；不把全部文件重新保存作为默认修复。
- 第三方插件、模板资源和证据归档仅在任务确实涉及它们时修改。
- 文档记载的工具能力不等于当前环境已接通。调用 MCP 或素材工具前检查真实工具、参数与连接；生成后检查素材，不宣称未运行的生成或测试已完成。PixelLab 角色制作的具体流程见[创建新角色流程与规范](../player/character_creation.md)。

## 目录、文档与证据维护

- 三份设计主文档继续按职责维护，不因子系统建目录就整体拆分。玩法事实属于玩法正文，剧情事实属于剧情正文；子系统规范解释如何设计、分层、实现与检验，不另复制一套玩法或剧情。
- 所有子系统规范、开发规则与流程文档放在 `docs/` 下。通用规则入口为本文；每个已开始的子系统使用 `docs/<system>/README.md` 作为独立目录入口，例如 `docs/player/README.md`。有实际内容后才建目录，不预建武器、任务等尚未开始的空目录。
- 每个子系统先维护一份入口文档；只有内容需要独立维护时才在同目录增加文件，并由入口引用。新增或移动入口时同步更新根 [AGENTS.md](../../AGENTS.md) 的路径和读取条件；根文件只保留索引，不复制完整规则正文。
- 文档目录与运行目录分离：`docs/player/` 存放角色规范，`entities/player/` 继续存放玩家脚本、场景和运行资源；武器代码与资源仍归现有 `items/weapons/`。不得因建立文档目录而移动无关代码、复制运行系统或把规范继续留在代码目录作为另一份权威正文。
- 参数和规则在一个位置维护。开发规范引用玩法规则，描述如何实现与检验；改变玩法时更新玩法正文及受影响的实现说明。
- 优先使用仓库内相对链接，便于移动或克隆；面向用户汇报文件时提供可点击的绝对路径。
- 资料归档和既有玩家反馈保留原始来源、样本范围与局限。不把便利样本频率当成总体支持率，不编造节省工时、生成成功率或留存数据。
- 制作成本按实际记录，数学估算标明假设；没有实测就写“待验证”。动画的生成次数、合格情况、修帧与适配时间按[创建新角色流程与规范](../player/character_creation.md)记录。

## 验证与交付

| 变更 | 最小验证要求 |
|---|---|
| 仅 Markdown | 检查链接、状态表述、规则一致性与改动范围，无需为文档运行游戏 |
| 脚本、场景、资源引用 | 检查 Godot 导入／解析，运行受影响场景并查看调试日志，记录未解决错误 |
| 动画与武器表现 | 在实际镜头与地图尺度中按[角色系统开发规范](../player/README.md)验证运行行为，按[创建新角色流程与规范](../player/character_creation.md)验收素材，编译通过不能代替画面检查 |
| 战斗与保存 | 覆盖这次变更影响的取消、生效、重复事件、死亡／倒地、保存重入等真实边界 |
| 联机 | 按影响范围验证房主与客机；容量验收需房主加七名客机跨设备，八个本地实例仅属于表现检查 |

检查通过后不无理由反复扩大测试。交付说明改了什么、为何这样改、实际验证了什么，以及尚未实现或未验证的部分；不能把计划、模板演示或单进程运行称为完整功能验收。
